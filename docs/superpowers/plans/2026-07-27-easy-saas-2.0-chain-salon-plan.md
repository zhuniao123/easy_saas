# easy_saas 2.0 连锁门店收银承载实施计划

> 对应验收合同：[easy_saas 2.0：连锁门店收银系统承载目标](../../wiki/easy-saas-2.0-chain-salon-acceptance.md)
>
> 执行原则：每个里程碑必须交付代码、可重复测试、示例配置、迁移脚本和验收记录；只完成文档或 UI 不算通过。

## 0. 里程碑总览

| 里程碑 | 交付目标 | 前置 | 通过后具备的能力 |
|--------|----------|------|------------------|
| M0 | 2.0 协议与质量基线 | 无 | DSL 可演进、变更可验证 |
| M1 | 多数据源业务执行 | M0 | PG 控制面驱动 MySQL/PG 业务库 |
| M2 | 统一 Region/State/Event Runtime | M0 | 复合页面共享内核 |
| M3 | MasterDetail | M1、M2 | 主从单据和整单动作 |
| M4 | Dashboard | M1、M2 | SQL 驱动多 Query 聚合页 |
| M5 | Workspace | M2、M3 | 收银/审批类复合工作台 |
| M6 | Transaction Hook 与一致性 | M1、M3 | 简单事务流、锁、幂等和审计 |
| M7 | Plugin/Outbox/Job | M1、M6 | 打印、短信、归档等可靠扩展 |
| M8 | 连锁门店参考验收 | M3～M7 | 2.0 发布候选 |
| E1 | 单终端 Edge Runtime | M8 | 2.1 离线单机候选 |
| E2 | 门店局域网 Edge Server | E1 | 2.2 多终端门店候选 |

M1 与 M2 可以并行；M4 可在 M3 后半段开始；M5、M6 需要共同收敛 Action 输入和草稿模型。

## 架构决策：Spring Boot 与部署形态

- 保留 Spring Boot，作为 JDBC/事务、Groovy Hook、权限、插件、Outbox 和 Job 的薄执行内核；
- 不为业务表生成传统 Entity/Repository/Service/Controller，不引入美容美发 Java Domain；
- 2.0 默认是中央服务，Electron 只作为打印、文件和本地设备 Client Bridge；
- Server 与未来 Edge 必须复用同一 Core，不能形成 Node/Java 两套业务执行语义；
- 单机离线能力安排在 E1/2.1，门店多终端安排在 E2/2.2；
- 若离线单机被提升为 2.0 硬目标，E1 必须移到 M8 之前，原 M8 改为最终联合验收。

| PG | PG | 必过 | 必过 | 必过 | 必过 |
| PG | MySQL | 必过 | 必过 | 必过 | 必过 |

### 完成标准

## M6：Transaction Action、Hook 与一致性

### 待办

- [ ] Transaction Executor 唯一持有连接、事务、超时、提交和回滚；
- [ ] `beforeValidate/beforeAction/beforeStatement/afterStatement/beforeCommit/afterCommit/onError/afterRollback`；
- [ ] Groovy Hook 使用窄接口：context、SQL asset executor、result、error；
- [ ] Hook 禁止自行 commit/rollback、任意取数据源和无限执行；
- [ ] Statement output 映射和后续 bind；
- [ ] Groovy 条件、简单分支、循环的资源上限；
- [ ] 行锁、乐观锁、锁顺序和冲突错误；
- [ ] 幂等键、请求去重和结果重放策略；
- [ ] 服务端金额使用 Decimal；
- [ ] 统一业务错误码和用户消息；
- [ ] Action 日志包含 SQL/Action/Script 版本；
- [ ] `afterCommit` 与事务内 context 明确隔离。

### 必测故障

- [ ] 第二条写 SQL 失败；
- [ ] assert 失败；
- [ ] Groovy 超时/抛错；
- [ ] 两个并发请求扣同一余额/库存；
- [ ] 相同幂等键重复提交；
- [ ] 客户端伪造金额、门店或用户参数；
- [ ] afterCommit 插件失败。

所有场景均需证明无部分业务提交，且日志能定位原因。

### 完成标准

## M8：连锁门店参考验收与发布候选

### 最小参考数据模型

- 门店、部门、员工与权限；
- 会员及余额；
- 商品/服务与库存；
- 订单、订单项目、挂单；
- 次卡及使用记录；
- 预约；
- Outbox/Job/审计。

允许简化参考项目字段，但不得绕开主从、事务、多门店、报表和插件验收目标。

### 端到端用例

1. 管理员配置 MySQL 数据源并生成基础资料页；
2. 店员只能访问授权门店和授权动作；
3. 新增会员，创建含服务和商品的挂单；
4. 恢复挂单并结算，原子写订单/行并扣余额、次数或库存；
5. 重复提交返回同一业务结果或明确拒绝；
6. 预约到店转换为待结算单据；
7. Dashboard 按门店、日期展示多 Query 聚合并钻取；
8. afterCommit 触发打印和短信模拟任务；
9. 插件失败进入重试/死信且订单保持成功；
10. 审计能还原用户、门店、SQL/DSL/脚本版本和执行结果。

### 发布阻断项

- 任一越权可由修改请求参数实现；
- 关键写入存在部分提交；
- MySQL 业务数据源只能查询不能事务写入；
- Workspace 依赖领域 React/Java 代码才能完成样例；
- 外部 I/O 在数据库事务内阻塞；
- 无法从日志确定所执行配置和 SQL 的版本；
- 双数据库组合集成测试不稳定。

## E1：2.1 单终端 Edge Runtime

### 待办

- [ ] 抽取可由 Server/Edge 共同依赖的 `easy-saas-core`；
- [ ] 使用 `jlink` 精简 JVM，Edge 作为 Electron 子进程受控启动和停止；
- [ ] 实现 H2 或 SQLite 业务方言、迁移、备份、恢复和故障测试；
- [ ] 定义签名 Runtime Bundle：Page/Entity/Action/SQL/Script/Plugin/i18n；
- [ ] Bundle 下载、签名校验、预验证、原子激活和上一版本回滚；
- [ ] 本地登录、权限快照、离线 Query/Action 和本地打印；
- [ ] 全局 ID、sync version、同步状态与软删除协议；
- [ ] 本地 Outbox、断点续传、幂等上行与中央确认；
- [ ] 总部资料下行和门店交易上行；
- [ ] 断网、进程崩溃、断电、磁盘空间不足、重复同步和升级测试；
- [ ] 明确共享会员余额/次卡的离线限制和操作提示；
- [ ] 本地 API 仅 loopback、进程认证、数据目录与安装目录分离。

### 完成标准

单台门店电脑在中央服务不可用时仍能登录、开单、现金类结算和打印；恢复网络后数据只同步一次，配置可安全升级和回滚，软件升级不覆盖业务数据。

## E2：2.2 门店局域网 Edge Server

### 待办

- [ ] 单一门店 Edge Server + PG/MySQL 本地数据库；
- [ ] 多 Electron/浏览器终端共享 Edge，禁止共享嵌入式数据库文件；
- [ ] 终端注册、设备身份、局域网 TLS/鉴权和健康发现；
- [ ] 多终端余额、库存、次卡并发锁和幂等；
- [ ] Edge 高可用、备份、远程诊断和升级策略；
- [ ] 中央与门店的冲突分类、人工处理和审计页面；
- [ ] 离线资产额度或联网强制策略。

### 完成标准

两个终端同时操作同一门店资产时不发生超扣或重复单据；中央断开期间门店内保持一致，恢复后能够审计全部同步与冲突处理结果。
